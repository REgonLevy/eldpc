# Notes for coding assistants

eldpc is an exact GPU BP+OSD-0 decoder for quantum LDPC codes (min-sum BP on the GPU, bit-packed
OSD-0 on the host, outputs bit-identical to the reference BP+OSD-0): Python package, C API, qLDPC spec.

## Where things are

- `src/core/`: the frozen decoder core, identical to the benched sources except that development-history
  comments were neutralised (code tokens and line structure: `TOKENS.sha256`, `tools/check_comment_only.py`;
  raw bytes: `SOURCES.sha256`). Never edit.
- `src/cpu/`: the optional CPU core (fastbpcpu6g), four frozen sources, with the same comment-only
  difference from the sources they came from (`test_cpu_sources.py`, `TOKENS.sha256`, `SOURCES.sha256`).
  Never edit them either.
- `src/third_party/ldpc/`: vendored ldpc sources the core builds on. Do not edit.
- `LICENSE` (Apache-2.0), `NOTICE`, `AUTHORS`, `THIRD_PARTY_NOTICES`: the licence files. Every new
  source file of the package gets a one-line `SPDX-License-Identifier: Apache-2.0` header, except
  the frozen and vendored files (`src/core/`, `src/cpu/`, the two frozen `decoder_abi.h` copies,
  vendored code).
- `src/port/`: the C API front (`eldpc_front.cpp`): picks the AVX2 or AVX-512 core at load time.
- `include/eldpc.h`: the fixed C API. `python/eldpc/`: the Python package (`Decoder`, presets, DEM
  conversion, `eldpc.qldpc`). `tests/`: the package tests.
- `verify/`: bit-identity suite against the reference (docs/VERIFY.md). `bench/`: C and Python
  latency, throughput and LER benchmark (docs/BENCH.md).
- `tuning/`: the `eldpc-tune` knob tuner (tuning/README.md), TUNER.md and KNOWLEDGE.md.
- `docs/`: ARCH.md (how the package is put together), BUILD.md, SUPPORT.md (supported hardware and
  software), QLDPC.md, VERIFY.md, BENCH.md, RESULTS.md (generated by docs/tools/make_results.py) and
  CLAIMS.md. `tools/`: small measurement and check scripts.

## Rules

- Exactness: no change may alter any output (correction, observables, status word, soft output) of
  any shot at the same problem and config. A faster change with different outputs is a bug. The
  CPU core must return exactly what the GPU core and the reference return.
- Never edit `src/core/` (`cd src/core && sha256sum -c SOURCES.sha256` must pass) or `src/cpu/`
  (`cd src/cpu && sha256sum -c --strict SOURCES.sha256` must pass; so must
  `python3 tools/check_comment_only.py --check`). No fast math, no FMA
  contraction, no `-march=native`: keep the exactness flags in `CMakeLists.txt` (docs/BUILD.md).
- After any change: `pip install ".[test,qldpc]"`, `ELDPC_REQUIRE_GPU=1 python -m pytest tests`, the tests of the
  part you touched (`python -m pytest tuning/tests`, `python -m pytest -q bench/tests`), and
  `python verify/run_verify.py --quick`, which must print PASS. On a machine without a GPU, run
  `CUDA_VISIBLE_DEVICES= python -m pytest -m cpu_core tests` (the CPU-core tests; no GPU needed)
  and `CUDA_VISIBLE_DEVICES= python -m pytest -m "not cpu_core" tests` (the rest passes or skips).
  On a machine without the CUDA toolkit, build with `ELDPC_WITHOUT_CUDA=1` (only the front and the
  two CPU cores; `python tools/cpu_only_build.py` reproduces and records that build).
- Every number in a document names its hardware and its source: a results file of this package
  (`docs/results/`, `tools/results/`, `tuning/data/`, `tuning/results/`) or a command that reproduces
  it. tuning/KNOWLEDGE.md also quotes development records that are not shipped; it labels each such
  number "development record", and those numbers cannot be re-checked from the package.

To tune eldpc for a code, a noise level or a machine, follow tuning/TUNER.md; facts, measured effects
and dead ends are in tuning/KNOWLEDGE.md.
